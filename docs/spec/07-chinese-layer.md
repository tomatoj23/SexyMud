## 0. 定位：中文层属于引擎，不属于内容

这是本引擎存在的核心理由，务必分清：

| 属于**引擎**（中文层） | 属于**内容**（武侠包） |
|---|---|
| 最长动词匹配、别名、消歧 | 「打」「杀」「往北走」这些具体动词 |
| CJK 显示宽度、避头尾折行 | 「不堪一击」「炉火纯青」这些词 |
| 人称代词渲染（你／他／她） | 伤害分档的具体措辞 |
| 中文检索（子串 + 拼音首字母） | 21 个部位表、量词、称谓表 |
| 中文排序 | 50 档造诣表的**内容** |
| UTF-8 全链路 | — |

**机制进引擎，词库进内容。**

## 1. 为什么这是我们的机会

英文 MUD 框架的几乎每一个文本假设，在中文下都不成立：

| 假设 | 英文 MUD | 中文现实 |
|---|---|---|
| 词之间有分隔符 | 空格分词 | **无空格** |
| 一个字符占一列 | 成立 | **全角占两列**，组合符占零列 |
| 动词随主语变位 | 必须处理 | **不变位**，但要换人称代词 |
| 标点 | 半角 | **全角**，且有避头尾规则 |
| 排序与检索 | 字母序 | **拼音序 / 笔画序 / 子串 + 拼音首字母** |

Evennia 是成熟的现代 MUD 框架，但它的 CJK 支持**只有 24 行**（`utils.display_len()`），而且**几乎没有被调用**——`evmore`／`ansi`／`text2html`／`evmenu` 全都没用它。

**这不是疏忽，是它的设计假设里没有中文。这就是我们的机会。**

## 3. 已定对策要点

### A. 输入
- **最长动词匹配**，不引入分词库（MUD 命令语法空间受限）
- 别名**长度降序**（防「笑」吃掉「笑傲江湖」）
- 别名两层：内容层（全局）+ 玩家层（存档 nicks，支持 `买 $1` 模板）
- 同一命令的 `verbs[]` 里中文与英文缩写并列（`北` / `n` / `north`）
- 消歧用「第 N 个 X」／「X·N」（不用 Evennia 的 `name-N`）

### B. 输出
- 自研显示宽度：**全角 = 2，组合符/变体选择符 = 0**，覆盖 emoji ZWJ 与控制字符
- **必须注入切块器本身**（Evennia 正是漏了这步）
- 切块时**重放未闭合样式 span**
- 中文无动词变位 → 不需 `$conj()`，只需人称代词
- 渲染 `(event, observerState)`，**按接收者逐一遍历**

### C. 叙事（借自 xkx100，这是金矿）
- **伤害分档文案矩阵**：同一结构 + 程度递进，最后档必带双感叹号
- 50 档造诣表（由数值推导，纯显示不设门槛）
- 21 个受击部位
- 量词（一柄剑／一把刀）
- 称谓随造诣变化（后生 → 少侠 → 前辈）
- 数值→文本统一为**区间表 → 中文词**，**引擎不给默认文案**

### D/E
- 中文模糊检索：**子串匹配 + 拼音首字母索引**（Lunr 对中文不友好）
- **不强制拉丁化角色名**（Evennia 的 `normalize_name` 是反例，它自己承认该重构）
