# 测试契约与输出层约定：命令测试骨架、per-observer 渲染、CJK 计宽、tick 化定时

**第三批 Evennia 借鉴**，定案七件事：**怎么测命令**、**文本怎么渲染**、**中文显示宽度**、**冷却与定时**、**分支内容怎么表达**、**输出流怎么切块**，并记录若干不借的项。

> **来源**：`D:\My_Projects\evennia-main`（Evennia）——`utils/test_resources.py`、`contrib/rpsystem`、`contrib/rpg/traits`、`utils/evmenu.py`、`utils/evmore.py`、`utils/gametime.py`、`contrib/utils/auditing`、`CODING_STYLE.md`，以及其源码模块分解。**只取抽象，不取技术栈。**

## Context

ADR-0016/0021 定了命令层与世界模型，ADR-0022 定了内容层的运行时契约。开工前还缺四件：

1. **怎么测？** 命令引入后，第一次出现「输入一行字 → 吐出一段有序文本」这种东西。没有测试骨架就写 M1，后面每改一次解析规则都要人肉验证。
2. **文本怎么渲染？** ADR-0021 定了 Actor stance（同一事件对当事人与旁观者不同文本），但没定实现形态。
3. **中文显示宽度**。这是个纯中文项目特有的问题，英文 MUD 框架帮不上忙。
4. **冷却 / 定时**。ADR-0022 §5 定了「按需求值」，但冷却这类具体机制还没定。

## Decision

### 1. 测试契约：命令测试骨架（最高优先级）

借鉴 Evennia 的 `EvenniaCommandTest.call(cmd, args, expected_output)`，四条规则：

**（a）不走真实分发器**。测试手工按序跑四段：`at_pre_cmd → parse → func → at_post_cmd`。这样解析与执行可以分别被测，也可以只测其中一段。

**（b）断言「输出消息序列」，不断言单条字符串**。把输出汇（output sink）换成注入的收集器，跑完取回**按调用顺序排列的消息数组**；用 `||` 分隔表达"这是两次独立的输出调用"。匹配用**前缀**而非全等——叙事文本有随机变体，全等会让测试脆弱且无意义。

**（c）不确定性四件套，全部注入**：
| 来源 | 注入物 |
|---|---|
| 时间 | `Clock`（引擎 tick 计数，不是 `Date.now()`） |
| 输出 | 输出汇（收集器，不是真实终端） |
| 世界状态 | 固定夹具（一份纯对象世界快照，无 IO） |
| 跨测试泄漏 | 每个用例结束后**显式清缓存**——不清会导致顺序相关的 flaky 测试 |

**（d）`inputs=[...]` 把交互变成可重放脚本**：需要玩家二次输入的流程（确认、选择、分页），用输入列表喂进去，跑完即一条完整的、可重放的会话脚本。

**（e）必须同时断言消息条数**。前缀匹配有个致命漏洞：**多吐一条错误的消息，测试照样通过**。因此断言 = 逐条前缀匹配 **+ 条数相等**。

**（f）多接收者必须显式列出**。测试只 mock 显式声明的接收者，其余输出会被丢弃。战斗播报是多目标的（当事人 + 旁观者），漏列接收者等于漏检。

> ⚠️ **Evennia 缺的一环，我们必须自己补**：它**不为随机设种子**（其 dice contrib 直接 `from random import randint`）。我们的确定性要求比它更严——**RNG 种子必须是第 5 个注入物，且种子进存档**。

> ⚠️ **Evennia 的 `.call()` 实现里有几处我们不要照抄**（源码级坑，见 ADR-0024 §2）：输入队列它用 `pop()` 从尾部取（顺序反）、`at_pre_cmd` 返回真值会静默跳过整段且不跑 `at_post_cmd`、无条件的正则会吃掉以 `| `／`--`／`+` 开头的正文行。

**验收标准**：M1 的每一条命令，都至少有一条 `call()` 用例断言其输出序列。

### 2. 渲染是纯函数 `(event, observerState) => string`

借鉴 rpsystem 的 sdesc / recog：**文本模板里只有引用，不写死名字**；渲染时按**每个观察者**分别替换成他认识的那个名字。

- 这样「同一事件、不同接收者、不同文本」（ADR-0021 §3 的 Actor stance）就有了一个可执行形态，而不是散落在各处的 if。
- 纯函数形态与 ADR-0017 的确定性天然契合：**同样的事件 + 同样的观察者状态 ⇒ 同样的字符串**。

### 3. 数值 → 文本的映射是内容，引擎不给默认文案

借鉴 traits 的 `descs`：`{10: "初窥门径", 50: "略有小成", 90: "炉火纯青"}` —— **数值区间直接产出中文词**，而不是显示裸数字。（档位名取自 xkx100 §5.1 的 50 档表，不得杜撰。）

- 造诣 50 档、伤害档（轻/中/重/濒死）、剩余气血档、状态描述，全是同一模式：**区间表 → 中文词**。
- 引擎**不得内建默认文案**（承 ADR-0022 §7 的红线）：模板里只有占位符，词由内容提供，否则英文词会渗进引擎，直接违反硬标准 1。

### 4. CJK 显示宽度必须自研

Evennia 的 `justify` / `crop` / `ANSIString` **全部按字符数计宽，没有 CJK 全角处理**——中文文本会折行错位。这是英文 MUD 框架帮不了的部分。

- 需要一个 `wcwidth` 式的**显示宽度函数**（全角 = 2，半角 = 1），供折行、截断、对齐使用。
- 这条是**纯中文项目特有的、不可回避的**工程项，M1 输出层就要有。

### 5. 冷却与定时一律存「到期 tick」，不存时间戳

借鉴 `cooldowns` contrib：`key → 到期 tick` 的只读查询表，`ready(key)` / `add(key, n)`。

- **存 tick 而非真实时间戳**，天然确定性，成本几乎为零。
- 与 ADR-0022 §5「按需求值」一致：到期判定是 `nowTick >= dueTick` 的比较，不是定时器回调。
- **引擎内禁止 `setTimeout` / `setInterval`**（ADR-0017 已有禁令，此处明确其替代品就是这个 tick 表）。

### 6. 分支内容用节点图，且「只被 parse，不被 eval」

借鉴 EvMenu 的模板语言的**性质**（不是它的语法）：

- 节点图 = `{ 文本, 选项[] }`，选项含 `key / desc / goto`，`goto` 指向**节点名**或**具名 effect**。
- **关键性质：内容只被解析，不被求值**。需要动态行为就退回**具名 effect 注册表**（引擎内的固定实现，内容按名引用）。
- 迁移到本作 = **JSON 节点数组 + 具名 effect 注册表**：引擎零主题词，内容零代码，且能被 JSON Schema 校验。
- 适用：NPC 对话、奇遇分支、任务链。（ADR-0016 已定任务本身不做对话树，但**奇遇与 NPC 对话**是这个形态。）

### 7. 输出流不做模态分页

Evennia 的 EvMore 是**模态的**——它用 `Replace` 合并命令集**劫持输入**来翻页。

- **在我们这里是反模式**：战斗输出是**追加式滚动流**，劫持输入会打断它。
- 只取「按显示高度切块 + 边界感知」，**不取 cmdset 劫持**。
- 分页/滚动是客户端职责（ADR-0018 的 `TerminalView`），配合 §4 的显示宽度函数。

## 记录：不借或改造的

| Evennia 的 | 处置 | 理由 |
|---|---|---|
| **命令 docstring 即游戏内 help** | **改造**：help 文本移到 JSON 内容，按命令 id 引用 | docstring 与玩家文本合一，是"框架即游戏"的残留；我们要内容可校验、可翻译 |
| **`.rate`（每秒真实时间）** | **改造**：改 tick 驱动 | 违反 ADR-0017 确定性 |
| **protfuncs 的 `$random()` / 值为 callable** | **不借**：改种子化白名单求值（ADR-0022 §3） | 违反确定性 |
| **EvMore / EvTable / EvEditor** | **不借**：React 有原生能力；EvMore 还是反模式（§7） | 全是"哑终端 UI"，我们发结构化 token 流 |
| **`funcparser` 的 `$func()` 内联脚本** | **不借**：改 schema 内的结构化节点 | 无法被 JSON Schema 校验，且通向软编码失控 |
| **Batch-Code Processor（执行任意 Python）** | **不借**：只取 Batch-Command 的"顺序构建 + 可重放"思想 | 与三条硬标准全面冲突 |
| **审计（auditing）的脱敏** | **改造后借**：它的"记录输入序列 + 输出序列"流水日志 = 我们的**确定性回放日志** | 隐私不是重点，回放才是 |
| **分层 import 顺序强制**（标准库 → 框架 → 引擎 → 贡献） | **借**：用 ESLint `import/order` + 边界规则，机械保证 `engine/` 永不 import `content/` | 这是硬标准 1 的**可执行保障**，比评审更可靠 |

## 记录：模块分解的启示

Evennia 把**调度**拆成了 4 个独立模块（`taskhandler` 延迟任务 / `tickerhandler` 周期 tick / `ondemandhandler` 按需求值 / `monitorhandler` 监视），命令拆成了 5 层（`command` / `cmdset` / `cmdsethandler` / `cmdhandler` / `cmdparser`）。

**一个成熟的 MUD 引擎认为值得独立成模块的关注点**：持久化包装、身份、命令解析、调度、权限、原型、帮助、协议、配置扩展点、内容。其中「调度」被拆到 4 个模块这一点最值得注意——**"时间"不是一个问题，是一组问题**。ADR-0022 §5 只选了 OnDemand 一种，M1 若出现周期刷新类需求，应当另立调度器而不是把逻辑塞进 OnDemand。

另：它的 `game_template/world/`（纯内容）与引擎代码不同目录——**再一次印证 JSON + Schema 硬门禁的方向**。

## Considered Options

- **端到端测试（起真实客户端、敲真实命令）**：被否——慢、脆弱、无法覆盖分支，且无法注入时钟与随机。
- **只断言最终状态、不断言输出文本**：被否——本作的核心产物就是叙事文本，不断言输出等于没测。
- **全等匹配输出字符串**：被否——叙事有随机变体，全等会让测试变成维护负担。用前缀匹配。
- **用 `setTimeout` 实现冷却**：被否——违反 ADR-0017；改用到期 tick 比较（§5）。
- **对话用内联脚本表达分支**：被否——无法被 Schema 校验，且是软编码失控的入口（§6）。

## Consequences

- **M1 的第一件事是搭测试骨架**，不是写第一条命令。骨架成本约一次性的百来行，但它决定了后面所有命令能否被放心重构。
- **引擎新增一个纯函数模块**：CJK 显示宽度。小但必需（§4）。
- **存档新增**：RNG 种子（§1d）。纳入版本化迁移链。
- **ESLint 配置需要加 `import/order` 边界规则**（§记录），这是硬标准 1 从"靠评审"升级为"靠工具"的一步。
- **ADR-0022 §5 的调度选择得到补强**：OnDemand 是默认，但不是唯一；将来加周期调度器时应另立模块。
