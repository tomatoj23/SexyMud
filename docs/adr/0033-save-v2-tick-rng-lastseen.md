# 存档 v2：tick、RNG 状态与 `lastSeenTick` 迁入，`Rng` 端口可导出

`spec/04` §1.4 留了一句硬话：v1 里没有引擎 tick 与 RNG 种子，「那一天是 v2 + 一条迁移，**不是往 v1 形状里静默加字段**」。那一天就是 M4。本文定三件事：`Rng` 端口怎么导出状态、v2 装什么、以及迁移与恢复的口径。

## Context

- `types.ts` 的注释写着「The seed lives in the save」，但端口今天只有 `next()` —— mulberry32 的 state 锁在 `createSeededRng` 的闭包里，**取不出来**。「种子进存档」至今落不了（ADR-0017、ADR-0023 §1 把它列为 Evennia 缺的那件东西）。
- ADR-0024 §2 要求确定性可复现；一个不可序列化的 RNG 会让「保存后重开」得到不同的随机序列。
- 迁移链机制自 M2-T5 就位，但**为空** —— 从未被真实迁移检验过。ADR-0003 要求「不造假迁移」。
- `spec/04` §1.4 已有一条成文口径：**在当前版本内中途落地的槽，恢复时一律可选**。`tags`（M3-T5）是这条规则的第一个用例。

## Decision

### 1. `Rng` 端口加强制的 `getState()`

```
Rng { next(): number; getState(): number }
```

mulberry32 的状态**就是一个 uint32**（我们可以指定实现了 `createSeededRng`，见 `rng.ts`），导出成本近乎为零，恢复 O(1)。

**强制**：宿主不可提供一个不可序列化的 RNG。ADR-0017 的确定性是三条支柱之一，一个不可序列化的随机源会让保存/加载不再是往返。

### 2. v2 载荷增加三样

| 槽 | 位置 | 为什么必须有 |
|---|---|---|
| `nowTick` | 顶层 | 引擎高水位（ADR-0031）。不存则恢复后时间倒退，`nowTick >= dueTick` 恒为假 ⇒ **冷却永远不到期**（不是"失效"） |
| `rngState` | 顶层 | `Rng.getState()` 的读数 |
| `lastSeenTick` | 每实体 | 该实体上次被结算到的 tick（ADR-0034 两层推进的实体那一半） |

### 3. 迁移补默认值

v1 → v2：`nowTick = 0`、`rngState = 0`、`lastSeenTick = nowTick`。

补的是「这份存档写下时那个字段还不存在」这一事实，不是猜测玩家状态。

### 4. 恢复口径：一律「缺即空」，不为 v2 新增槽加特例

与 §1.4 那条规则同一个口径。**多一条规则就多一处将来对不上的地方。**

> ⚠️ 代价（措辞要准）：v2 存档若 `nowTick` 丢失或损坏**不会报错**，游戏当成第 0 tick 继续跑 ⇒ 判定 `nowTick >= dueTick` 恒为假，**冷却不是「失效」，而是永远不到期**（技能要再等满 `dueTick` 个 tick）。这比「失效」更糟，但仍属「时间回到过去」这一类可恢复的问题，且比多养一条检测规则便宜。

### 5. 顶层槽的进出通道是一个签名问题

今天 `serializeWorld(world)` 只收一个 world、`restoreWorld(snapshot) → WorldState` 只返一棵树（`WorldState = { entities }`），而高水位按 ADR-0031 住在**驱动世界的那一侧**，不在 `WorldState` 里。于是 `nowTick`／`rngState` 既写不进也读不出。三个选项见 `spec/04` §1.5 第 3 条，倾向 `serializeWorld(world, meta)` ／ `restoreWorld → { state, meta }`。**实现前必须选一个，否则 T6 卡住。**

### 6. 不做 v2 → v3 连迁

v2 的形状这一次要想全。因此 **`nicks`（玩家层别名，`spec/02` §8 至今未勾）不同趟** —— 它是**玩家层**不是实体层；把两层的东西塞进同一次迁移，正是走向连迁的最快方式。等别名票自带那趟。

## Considered Options

| 方案 | 否掉的理由 |
|---|---|
| **只存初始种子 + 快进 N 次 `next()`** | 恢复是 O(N)，N 随存档年龄**无界增长**；且需要额外存一个「已调用次数」，本质上就是自己实现了一遍 state |
| **种子不进存档，每会话现生成** | 与 ADR-0017「确定性／可重放」直接冲突；同一场战斗在保存/重开之后无法复盘 |
| **v2 新增槽在恢复时必填校验**（v2 写出的存档一定带它们，缺 = 损坏） | 为 v2 破 §1.4 的例；多一条规则多一处漂移 |
| **v1 存档不迁移，大声失败** | 「首条真实迁移」形同虚设；ADR-0003 明确要等真实迁移来检验这套机制 |

## Consequences

- `SAVE_VERSION` 1 → 2，迁移链机制**第一次被真正行使**。
- `serializeWorld` 的规范序要覆盖新槽（`nowTick`／`rngState` 是标量；`lastSeenTick` 随实体；`cooldowns` 是对象，键要排序）。
- `createSeededRng(state)` 一身二用：既是「新建」也是「恢复」。不另开 `restoreRng` —— 参数都是同一个 uint32，分两个函数反而让人以为它们的语义不同。
- 有了 `rngState`，「同一条命令序列重放得到同一结果」才算真的闭环（此前 RNG 依赖测试硬塞一个种子，ADR-0023 §1 的第五件注入依赖）。
