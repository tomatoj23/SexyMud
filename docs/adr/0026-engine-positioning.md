# 我们做的是引擎：中文优先的确定性文字 MUD 引擎（附一个武侠内容包）

**定位升级**：本项目不是「一个武侠 MUD 游戏」，而是**一个更适合中文的确定性文字 MUD 引擎**，武侠是它装载的第一套内容包。三条硬标准由此从「开发纪律」升级为「产品定位」。

## Context

项目启动时（ADR-0004）就定了「引擎与内容完全分离」，但当时的心智模型是**做游戏，引擎是副产品**。五轮调研（Evennia + xkx100，共 25 个子代理）之后，两件事让这个模型站不住了：

1. **硬标准 1 被反复印证**。Evennia（现代 MUD 框架的代表）独立得出了同样的结论：「framework not game」「code and data are kept separate」，且它的 `game_template/world/`（内容）与引擎代码不同目录。**世界上最大的现代 MUD 框架，核心哲学和我们第一天定的是同一件事。**
2. **中文是空白地带**。Evennia 的 CJK 支持只有 24 行且几乎没被调用；它的解析器假设空格分词；它的角色名强制拉丁化。而 xkx100（原生中文 MUD）有全套中文叙事资产，却没有工程性——LPC 文件**同时是代码、是数据、是内容**。

**这不是两个参照物的取舍，而是一次分工**：Evennia 提供架构，xkx100 提供中文叙事，我们补上两者都缺的东西。

## Decision

### 1. 定位：中文优先（Chinese-first）的确定性文字 MUD 引擎

三条支柱，缺一不可：

| 支柱 | 含义 | 为什么是差异化 |
|---|---|---|
| **中文是一等公民** | 中文的输入、显示、叙事、检索不是适配层，是设计起点 | Evennia 的中文支持≈0；xkx100 有中文但没有工程抽象 |
| **确定性** | 禁 `Math.random()`／`Date.now()`／定时器；时间走注入的 tick 计数，随机走注入的种子 | **两者都没有**，也不可能有（Evennia 全栈墙钟+异步，xkx100 是 2002 年的 LPC）。这是我们能做出的、它们结构上做不到的东西 |
| **内容即数据** | 全部 JSON + JSON Schema 硬门禁；引擎零题材词、零硬编码数量 | Evennia 是「代码 + DB」，xkx100 是「LPC 文件即一切」。我们的 `content:check` 比两者都严格 |

### 2. 取长补短：三者的分工

| 能力 | Evennia | xkx100 | 我们取谁 |
|---|---|---|---|
| 命令集合并栈、优先级与合并规则 | ✅ 强 | ❌ | **Evennia**（ADR-0021） |
| 原型继承、锁/条件表达式、标签 | ✅ 强 | ❌ | **Evennia**（ADR-0022） |
| 调度（4 个调度器各自成模块） | ✅ 强 | ❌ | **Evennia 的思想**（ADR-0022 §5、ADR-0025 §三） |
| 中文战斗文本分档矩阵（伤害档 → 措辞） | ❌ | ✅ 强 | **xkx100**（ADR-0011） |
| 50 档造诣表、21 部位表、量词、称谓 | ❌ | ✅ 强 | **xkx100**（ADR-0019、ADR-0020） |
| 房间/出口/门派/任务的内容组织 | ⚠️ 有但弱 | ✅ 强 | **xkx100**（`docs/research/xkx100-content-structure.md`） |
| 确定性、可重放 | ❌ | ❌ | **我们独有**（ADR-0017） |
| JSON + Schema 硬门禁 | ❌ | ❌ | **我们独有**（ADR-0003） |
| 多端结构化输出（非 ANSI、非终端仿真） | ⚠️ 有 webclient 但是终端仿真 | ❌ | **我们独有**（ADR-0018） |
| 命令测试契约（断言输出消息序列） | ⚠️ 有但有缺陷 | ❌ | **改进版**（ADR-0023 + ADR-0024 §3） |
| 中文输入/显示/检索 | ❌ 24 行且没调用 | ⚠️ 有实践无抽象 | **我们独有**（`docs/chinese-mud-concerns.md`） |

### 3. 我们明确不借的（这也是定位的一部分）

- **不借「代码即内容」**（xkx100 的 LPC 文件、Evennia 的 typeclass）。内容必须是可被 Schema 校验的纯数据。
- **不借终端仿真**（Evennia 的 ANSI → HTML 双转换管线、EvMore 模态分页）。我们发结构化 token。
- **不借模态菜单作为主交互**（EvAdventure 的证据：大半开发量花在绕开 EvMenu 的模态性，整个游戏只新增 5 条命令）。
- **不借 per-object timer**。一律纯函数 + 到期桶 + 区域 tick（ADR-0025 §三）。
- **不借 attribute handler**（那一千行是在为 SQL↔Python 阻抗失配买单，我们没有这个失配）（ADR-0025 §二）。

### 4. 验收标准：从「好不好玩」变成「能不能换内容」

做游戏的验收是「好不好玩」；**做引擎的验收是「别人能不能用它做出第二个游戏」**。

具体三条，可测：

1. **题材中立**：引擎源码里搜不到任何题材词（已有纯度测试，且它真的会报错）。
2. **换内容不改代码**：换一套非武侠内容包（比如仙侠或科幻），引擎**不改一行代码**即可运行。
3. **中文无损**：中文输入、显示、折行、检索在**所有端**（Web／小程序／APK）表现一致且正确。

> 第 2 条目前**尚未验证**——这是我们离「引擎」最近的缺口，也是最该优先补的（见 Consequences）。

### 5. 对三条硬标准的影响

三条硬标准**不变，但性质变了**：

| 硬标准 | 原定位 | 新定位 |
|---|---|---|
| 1. 引擎与内容完全分离 | 开发纪律 | **产品定义**——它就是引擎之所以是引擎的原因 |
| 2. 面向未来 | 工程远见 | **架构契约**——确定性、可迁移、可测试，是引擎对外承诺的能力 |
| 3. 依赖环境自包含 | 环境约束 | **不变**（仍是硬约束，ADR-0007） |

### 6. 需要一份能力文档，而不只是 ADR

ADR 记录「为什么这么定」，**不记录「你能用它做什么」**。一个能被别人用的引擎，需要面向使用者的能力文档——这正是 Evennia 做得好的地方（43 个 Components 文档 + 18 个 Concepts）。

因此新增一处文档区：**`docs/chinese-mud-concerns.md`**（中文特有问题全景，已落）。它的定位是「设计研究清单」，不是 ADR——只列问题与对策，作为引擎的**需求来源**。

后续 M1 落地时应按子系统补齐能力文档（命令层、世界层、状态层、时间层、输出层、内容层）。

## Considered Options

- **维持「做游戏」定位，引擎只作为内部实现**：被否——那三条硬标准的成本（Schema、Registry、校验、纯度测试）就变成了纯开销，只有在「引擎是产品」时才是有意支付的投资。
- **做成通用引擎，中文作为可插拔适配层**：被否——Evennia 就是这条路的结果，中文支持最终退化成 24 行且没人调用。**中文必须是设计起点，不是适配层。**
- **照搬 xkx100 的中文内容体系并把它写进引擎**：被否——那会让题材词进引擎，直接违反硬标准 1。中文叙事的**机制**（分档、区间表、部位表）进引擎，**词库**进内容。

## Consequences

**立即可做的（零风险，收益最高）**：

1. **做一次「换内容」演练**（验证 §4 第 2 条）。不需要真写第二套内容——只要把现有 `content/` 里所有**武侠语义**的字段挑出来，确认引擎是否真的不解释它们。已知待查：`resources.json` 的 `kind: "progress"`（引擎只读不分支，应无碍）、活动 id 的语义（`act-practice` 是内容 id，应无碍）。
2. **把待定的中文项定掉**（`docs/chinese-mud-concerns.md` 的 A6／B8／B9／D1／D4／E3）。其中 **B8（避头尾折行）与 D1（中文排序）** 会在内容量上来后变得昂贵。
3. **补一条 UTF-8 存档往返测试**（E3）——最便宜的一条，且属于 ADR-0025 §九 说的「边界」类测试。

**中期（M1）**：

4. 按 ADR-0025 的代价排序开工：**命令测试骨架 → 中文解析器 → `commands/` `rooms/` `npcs/`**。
5. `actorId` 与事件侧 `seq` 在写第一条命令时就带上（ADR-0025 §一）。
6. 每个子系统落地时，同步补该子系统的能力文档。

**需要重新审视的**：

7. **包名与仓库定位**。当前是 `@sexymud/*`，内含 `core`（引擎）与 `web`/`editor`（宿主）。若引擎要能独立发布，`packages/core` 应视为**可发布的库**，而不是游戏的内部目录——这会影响它的 README、导出面与测试策略。
8. **文档地图需要区分「引擎文档」与「内容文档」**。`HANDBOOK.md` 目前两者混排；随着内容量增长会变得难用。
