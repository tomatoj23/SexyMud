# 原型继承：加载期展平、注册表内、同集合

ADR-0022 §3 定下了原型继承的合并规则，并留下一句硬话：`prototypeKey` / `prototypeParent` 两个字段**第一天就预留——字段是零成本，事后加才是灾难**。12 张票过去，`schemas/`、`packages/core/src/`、`content/` **三处 0 命中**。M3 是在还这笔债。本文定五件事：展平时机、展平落点、继承作用域、字段形态、环怎么防。

## Context

spec/03 §6 已定合并规则（**只有 `attrs` 与 `tags` 互补合并，其余键整体替换**）与三处必补（归一化 / 环检测 / `prototypeKey` 禁止继承），ADR-0024 §7 追加了理由。没定的是**机制**：

- **`createContentRegistry` 收的是主机已解析好的条目数组**，只做 id 唯一性与引用完整性，**没有任何加载期加工的钩子位**——展平插在哪一侧是空白。
- **展平与引用完整性校验的先后**没人规定。这不是审美：房间从原型继承来的 `exits` 与放置清单**要不要被引用校验**，决定了展平是不是一个绕过校验的后门。
- M2-T6 把「换包不改代码」（验收标准 2）做成了**结构保证**：非武侠迷你包经**同一装配路径**跑通。展平若放主机侧，这条保证退化成**纪律**——两个主机各实现一遍，一致性靠人。
- Evennia 的原型合并是**非纯函数**（原地改 dict），且它自己在 `objects.py` 里承认「we don't check for infinite recursion here」。

## Decision

### 1. 加载期展平，不是运行时求值

内容在构建期固定，不存在「父原型改了子体要热跟随」的需求。运行时求值换不来任何东西，只换来确定性风险：要缓存（Evennia `_CMDSET_MERGE_CACHE` 是 ADR-0024 记录的坑），而快照只存 id、M2-T5 的 `attachEntity` 重挂路径本不必知道继承这件事。

### 2. 展平在注册表内，顺序 = id 去重 → 展平 → 引用完整性校验

顺序不是审美。**展平必须发生在引用完整性校验之前**：继承来的 `exits`、`objects` 放置清单、`monsterId` 引用，全都要被校验，否则「把字段放进原型里」就成了绕过校验的后门。

放主机侧则更糟：M2-T6 的全部卖点是「换包不改代码」由**结构**保证，一旦展平在主机侧，「同一装配路径」就退化成靠纪律维持。注册表是 spec/00 定义的「引擎读取内容的唯一通道」，展平属于这条通道上的不变式。

### 3. 同集合内继承，不开 `prototypes/` 集合

跨集合继承（房间继承怪物）形状上无意义，而引用完整性校验本来就按集合做。原型条目**塞在被继承的集合里**，与「普通条目」的形状差别是零——多带一个 `prototypeKey`。开新集合要动 spec/06 的集合清单，换不来任何形状上的收益。

### 4. `prototypeKey` 的值 = 条目 id；展平结果剥掉 `prototypeParent`、保留 `prototypeKey`

- 继承引用写 `prototypeParent: [<父条目 id>]`；`prototypeKey` 的值必须与该条目自己的 id 相同（schema 表达不了，由注册表校验）。
- 于是**唯一性免费**（id 已唯一）、**零第二 id 空间**，而「显式声明才可被继承」的语义完整保留：没声明 `prototypeKey` 的条目被引用时，注册表**大声失败**。
- 展平结果**剥掉 `prototypeParent`**（它是已消费的指令，留着会让运行时误以为还能再展平一次），**保留 `prototypeKey`**（它是条目的属性）。配合 spec/03 §6 的「`prototypeKey` 禁止继承」，子体不会因继承拿到父的 `prototypeKey`——**没自己声明的条目展平后就没有 `prototypeKey`，也就不可被继承**。这是构造性保证，不是约定。

### 5. 环检测双保险

- `content:check`（离线门禁，内容作者提前发现）
- 注册表展平时（运行时保证，**不信任输入**）

按 ADR-0003 的分层，环是**引用**性质而非形状性质，所以两边都管——注册表对所有其他引用都是大声失败，环没有理由例外。

### 6. 合并后字典序升序 + 去重

spec/03 §6 警告过「合并非纯函数，我们要保证**可复现的输出顺序**」。顺序**不承载语义**（标签是集合，不是序列），所以规范序最稳，且与引擎既有先例同律（`sortedValues` 按 id 升序、`occupantsOf` 按 id 升序）。

否掉「按维度表顺序排以保留内容作者的分层意图」：维度表的顺序会随内容演进变化，会导致同一份内容在不同时期产出不同字节。

### 7. 只做 `tags`，不做 `attrs`；但合并律按同律一并实现

展平器**同时实现 `attrs` 的互补合并**（规则与 `tags` 对称，成本近零），等它有真实消费者（修饰符系统）时零改形。但 **`attrs` 不进 schema**——schema 全是 `additionalProperties: false`，为它开口子等于提前承诺一个还没设计的形状。展平器的 attrs 合并律由**合成测试**行使（测试数据是裸对象，不经 schema）。这与 M2-T4「接缝先行、合成驱动」同律。

### 8. 归一化交给 schema，不写加载期 homogenize

Evennia 在合并**前**跑 `homogenize_prototype`（`aliases` 强制成 list、tags 补 3 元组、`None` → `[]`/空串）。我们的 JSON Schema **直接要求规范形态**（spec/03 §6 已这样定），加载期不做归一化——schema 是门禁，`content:check` 会先拦下来。

## Considered Options

- **运行时求值（保留继承链、按需合并）**：被否——需要缓存（Evennia 的已记录坑），而内容构建期固定，热跟随无需求；还会让 `attachEntity` 的恢复路径必须知道继承。
- **展平在主机侧**：被否——M2-T6 的「换包不改代码」由结构保证，退化成纪律就白做了。
- **独立 `prototypes/` 集合**：被否——要动 spec/06 的集合清单，而带 `prototypeKey` 的条目与普通条目形状零差别。
- **跨集合继承**：被否——形状无意义，且引用完整性按集合做。
- **`prototypeKey` 用独立 id 空间**：被否——多一个唯一性要管；用 id 也能保留「显式声明」的语义。
- **环检测只做 `content:check`**：被否——注册表对其他所有引用都是大声失败，环没有理由例外；离线门禁只覆盖跑过它的内容。
- **按维度表顺序排**：被否——表顺序会变，破坏「同内容同字节」。

## Consequences

- `createContentRegistry` 的签名要变：新增**维度表**入参（可选），并按集合分别展平。
- 展平期错误一律**大声失败**：未知父 id、环、`prototypeKey` ≠ id、引用了未声明 `prototypeKey` 的条目。
- **13 个条目集合**的 schema 统一加 `prototypeKey`/`prototypeParent`（`config` 三类与 `condition` 除外）。
- `content:check` 要加**原型环检测**（它是跨文件的引用图，schema 表达不了）。
- 迷你包要**真的用上继承**（三个舱室继承一个舱室基类），作为「原型零题材耦合」的证据。
- 展平后的条目**没有 `prototypeParent`** → 运行时不可能二次展平，这是构造性的。
- **已知空缺**：`attrs` 的合并律只有合成测试行使，没有真实内容。
