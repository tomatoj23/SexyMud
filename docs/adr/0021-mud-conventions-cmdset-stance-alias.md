# MUD 传统约定：命令集合并与出口即命令、第二人称视角、双层别名

补齐 ADR-0016 缺的三件 MUD 基础设施：**可用命令是多源合并的结果**（不是一张固定表）、**出口是一等公民且方向即命令**、**视角与别名**。同时记录 Evennia 对本作既有决策的三点外部印证。

> **来源**：一手调研 `D:\My_Projects\evennia-main`（Evennia，Python MU\* 框架）的理念与抽象；题材与文本传统参照 `docs/research/xkx100-*.md`。**只借鉴理念与抽象，不借鉴技术栈**（本项目仍是 TS + React）。

## Context

ADR-0016 定的命令层是**一张全局命令表**：查表 → 执行。这撑得起「打 / 看 / 走」，但撑不起 MUD 的空间感。三个具体场景会失败：

> ⚠️ **2026-09-01 修订**：原文此处写「**分词** → 查表 → 执行」，该说法已由 **ADR-0024 §1** 废止——**中文无空格，不做分词**，改用**最长动词匹配**（别名按长度降序）。管线现为：**最长动词匹配 → 玩家别名替换 → 合并命令集 → 查表 → 参数解析 → 前置校验 → 执行 → 吐事件**。另：ADR-0016 原定的「单一全局命令表」也被本文§1 的**命令集合并栈**取代。

- 走进一间黑屋，`look` 应该变成「你伸手摸索，只触到冰冷的石壁」
- 只有骑在马上时，`下马` 才是一个存在的命令
- 房间里有一尊佛像，`参拜` 这个命令只在这个房间里有效

Evennia 用 **CmdSet 合并栈**解决这类问题，且这是它最强大的抽象：**可用命令 = 会话 + 角色 + 携带物 + 所在地 + 周围物件 + 出口，按优先级与合并规则在每次输入时动态合成。**

## Decision

### 1. 命令集（cmdset）分层与合并

可用命令不是静态表，而是**多源合并**的结果。合并源与优先级（借鉴 Evennia 的默认分层）：

| 源 | 优先级 | 提供什么命令 |
|---|---|---|
| 会话 | −20 | 与客户端相关的命令（清屏、字体、换行宽度） |
| 玩家 | −10 | 个人命令（别名、设置） |
| 角色 | 0 | 角色自身命令（武功、装备、状态） |
| 携带物 | 0 | 身上/手中物品提供的命令（「读 秘籍」） |
| 所在地（房间） | 0 | 房间提供的命令（「参拜 佛像」） |
| 周围物件 | 0 | 房间里可交互物件提供的命令（「推开 窗」） |
| **出口** | **+101** | 方向词（北／南／上／出…），**永远可用** |

合并规则（每条命令集自带，全是**内容字段**）：`mergetype` ∈ { **Union**（默认）／ **Replace** ／ **Remove** ／ **Intersect** } + `priority`。

**为什么这必须是内容而不是引擎逻辑**：加一个「黑屋里 look 变摸黑」= 加一条命令集条目 + 一条 `condition`，引擎零改动（硬标准 1）。Evennia 用 Python 类实现 CmdSet，我们不这么做——我们的命令集是 JSON 内容条目。

### 2. 出口是一等公民，方向即命令

出口**不是房间的一个字段，而是独立实体**（对应 Evennia 的 Exit 类型），它把自己注册成命令——「北」「n」「north」「往北走」都是它的 `verbs`。

- 门禁挂在出口上：拒绝文案是内容字段（xkx100 的 `valid_leave`：少林山门禁女客、禁持兵刃）
- **中文 MUD 要点**：方向词必须支持中文（北／南／东／西／上／下／进／出）与英文缩写（n/s/e/w/u/d），别名并列在内容里

### 3. 视角采用 Actor stance（第二人称）

同一事件，不同接收者看到不同文本：

| 接收者 | 读到 |
|---|---|
| 当事人（你出手） | 「你一剑刺向他的左肩。」 |
| 当事人（对手出手） | 「黑衣人一剑刺向你的左肩。」 |
| 旁观者 | 「黑衣人一剑刺向张三的左肩。」 |

- **中文红利**：中文无动词变位（「你捡起」=「他捡起」），只需处理**人称代词**替换（你 ↔ 我 ↔ 他/她），比英文的动词变位 + 代词双套机制**简单一个数量级**
- 因此 ADR-0011 的槽位体系需**新增一个视角维度**：同一模板按输出对象渲染出不同人称。`{attacker}` 输出给当事人时是「你」，输出给旁观者时是「黑衣人」
- 单机阶段没有旁观者，但 **NPC 在场时仍需第三人称**。**第一天就做对**——否则联网时要重写全部战斗文本（ADR-0011 的 13 槽位全部要返工）

### 4. 双层别名

| 层 | 归属 | 例子 |
|---|---|---|
| **内容层别名** | `commands[].verbs[]`，全局，所有人可用 | 「打」「杀」「attack」「kill」指向同一命令 |
| **玩家层别名** | 存档字段（nicks），个人，玩家自设 | `alias n = 往北走`；支持模板 `alias 买 $1 = 从 掌柜 买 $1`；支持对象别名「把我的马叫作乌骓」 |

中文输入成本高于英文（尤其移动端），**玩家自定义别名是刚需**，不是锦上添花。玩家层别名存存档，纳入版本化迁移。

### 5. Evennia 对本作既有决策的三点外部印证（不新增决策，记录佐证）

| Evennia 的做法 | 印证了本作 |
|---|---|
| **Zones 用标签而非引擎结构**：「Many MUD codebases hardcode zones as part of the engine and database. Evennia does no such distinction.」 | ADR-0008 的**归属字段化、不做目录分层** |
| **Portal / Server 分离**：Portal 懂协议不懂游戏，Server 懂游戏不懂连接方式；可重载 Server 而玩家不断线 | ADR-0017 的 `Authority` / Transport 端口隔离 |
| **框架而非游戏**：「we don't prescribe any combat rules, mob AI, races, skills, character classes」 | 硬标准 1（引擎与内容完全分离） |

三条都不是新决定，但**一个成熟的现代 MUD 框架独立得出了与本项目第一天相同的结论**，这提高了我们对这些决策的信心。

### 6. 本作相对传统 MUD 的新东西（要保留，不要被传统同化）

借鉴传统不等于回到 LPC。以下能力是本作的结构性优势，传统 MUD（含 xkx100）**做不到**，必须保留：

| 本作独有 | 传统 MUD 的形态 |
|---|---|
| **声明式修饰符聚合引擎**（效果 = 数据） | 效果硬编码在 LPC 文件里 |
| **七系结构签名 + 战斗摘要 + 同对手对照**（ADR-0020） | 无（没有「你这次比上次快了多少」的反馈） |
| **内容全 JSON + Schema 校验 + `content:check` 硬门禁** | 无校验，改错一个文件服务器起不来 |
| **50 档造诣 + NPC 敬称** | 有造诣档位，但敬称是静态的 |
| **确定性模拟（禁 `Math.random()`／`Date.now()`）+ 可搬服务端**（ADR-0017） | 无确定性概念，无法对拍与重放 |
| **版本化存档迁移链** | 存档格式变更即毁档 |

一句话：**用 MUD 的骨架与手感（房间、出口、命令集、别名、视角），跑本作的引擎（修饰符、七系签名、确定性模拟、内容校验）。**

## Considered Options

- **沿用 ADR-0016 的全局单一命令表**：被否——做不到「黑屋里的 look」「船上的划船」「房间里的参拜」，而这些正是 MUD 空间感的来源。
- **照 Evennia 把 CmdSet 实现成代码类**：被否——Evennia 这么做是因为它用代码定义游戏；本作用内容定义游戏，命令集必须是 JSON 内容条目（硬标准 1）。
- **只做当事人视角，忽略旁观者**：被否——联网后要重写全部战斗文本，代价高昂且不可逆。
- **别名只做内容层**：被否——中文输入成本高于英文，个人习惯差异大；xkx 老玩家自带按键肌肉记忆。
- **照搬 Evennia 的 `$You()/$conj()/$pron()` 内联函数语法**：被否——那是英文语法的产物（动词变位、反身代词）；中文只需人称代词替换，机制应更轻。

## Consequences

- **ADR-0016 的命令层需要扩展**：`commands/` 集合的条目要能声明「我属于哪个命令集」「我的 `priority` 与 `mergetype`」。引擎逻辑不变，只是查表前多一步「合并集合」。
- **`rooms/` schema 必须包含**：`exits`（出口表：方向 → 目标房间 + 门禁条件 + 拒绝文案）、`objects`（放置清单：实体引用 + 数量）、`enterText`（进入文本）。这与 xkx100 调研的房间四要素（出口图节点 + 描述文案 + 放置清单 + 规则）一致。
- **ADR-0011 需新增视角维度**：后果句的主语（ADR-0011 第 9 条）与槽位渲染要按接收者变化。
- **存档新增两张表**：玩家别名（nicks）、同对手交手记录（ADR-0020 §3 的 `lastEncounter`）。均纳入版本化迁移。
- **命令解析管线的顺序**：**最长动词匹配**（不分词）→ 玩家别名替换 → 合并命令集 → 查表 → 参数解析 → 前置校验 → 执行 → 吐事件。
