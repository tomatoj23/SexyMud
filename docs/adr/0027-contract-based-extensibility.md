# 扩展模型：内核 + 六条契约 + 可选机制模块，现在不做插件系统

引擎要覆盖从「最小 MUD」到「接近承载上限的复杂 MUD」的光谱。本文定案扩展方式：**三层模型（内核 / 契约 / 机制模块）**，扩展靠**契约**而非插件加载器，**现在不做插件系统**。

## Context

引擎定位（ADR-0026）确定后，需要回答：如何让它既能跑最小 MUD（房间 + 移动 + 看 + 命令），又能承载复杂 MUD（战斗、技能、经济、生产、任务、NPC AI、派系、时间季节、玩家组织…）？

「高度模块化」是直觉答案，但这个词有四种含义，它们对架构的影响完全不同：

| 类型 | 含义 | 评价 |
|---|---|---|
| 插件化 | 核心 + 可选包，按需加载 | 直觉最接近，**但现在不该做** |
| 分层 | 底层 → 机制 → 玩法，依赖单向 | 要 |
| **横切契约** | 定义模块之间**怎么说话** | **这才是关键** |
| 数据驱动扩展 | 加数据不加代码（枚举池） | 已在做（硬标准 1） |

两种极端都不可取：
- **厚地基**（把战斗经济做进核心）：做不到最小，且锁死用法。Evennia 刻意不做战斗正是因为此。
- **薄内核 + 全插件**：插件之间无法配合，会形成隐式耦合网（Eclipse／OSGi 的教训）。

## Decision

### 1. 三层模型

| 层 | 内容 | 可选性 |
|---|---|---|
| **内核** | 实体、位置与移动、命令、事件、时间、持久化 | **必需，且必须完备** |
| **契约**（六条） | 效果／条件／事件／状态／命令／时间 | 必需 |
| **机制模块** | 战斗、经济、生产、任务、技能… | **可选** |

- 最小 MUD = 内核 + 零个机制模块（已经能玩：走、看、说）
- 复杂 MUD = 内核 + N 个机制模块，模块间**通过契约交互，不互相 import**

### 2. 内核要「完备」，不是「最小」

| | 含义 |
|---|---|
| 最小 | 能跑就行，缺的以后加 |
| **完备** | 该有的概念都有（**尤其 hook**），但每个做到最简 |

例：移动的最小实现是 `go <方向>`；**完备但最简**的实现是「带 `moveType` 的原子操作 + hook 组」。后者不复杂，但 hook 让上层能挂东西；前者以后改起来要动所有调用点。

**内核的完备性体现在 hook 上，不体现在功能上** —— 即 ADR-0025 §五 那九项。

### 3. 六条横切契约（模块化的真正载体）

| 契约 | 让什么成为可能 |
|---|---|
| **效果** | 技能改战斗数值，不用 import 战斗 |
| **条件** | 所有门槛统一，且能被 Schema 校验 |
| **事件** | 系统间通过事件解耦 |
| **状态** | 存档与迁移统一 |
| **命令** | 可用命令可合并、可被别名、可被门禁 |
| **时间** | 无隐式定时器，保持确定性 |

**复杂度论证**：把功能切成块、块间直接互调 → **N²** 调用网；用契约交互 → **N**。

战斗模块不需要 import 技能模块：技能通过效果契约影响战斗，战斗通过事件契约通知技能（"命中了" → 加熟练度）。

### 4. 现在不做插件系统

**理由**：
1. 目前只有一套内容包（武侠），为假想的第二套设计插件加载器是**最典型的过度设计**。
2. **模块边界需要真的实现过才知道**。现在连第一个机制都还没有，设计机制间的插件接口是纯猜测。
3. **边界定错比不做更痛**——插件间会形成隐式依赖网，改起来比单体难受。

**何时做**：当第二套内容包需要复用内核时，把已实现的机制**抽**成模块。那时边界已知，**抽取是重构，不是设计**。

> **先做对，再拆开** —— 而不是先拆开再填。

## Considered Options

- **厚地基（战斗/经济/技能进核心）**：被否——做不到最小，且锁死用法。Evennia 不做战斗就是明证。
- **微内核 + 全插件**：被否——插件间无法配合，会形成隐式耦合网。
- **现在就建插件加载器**：被否——YAGNI，且边界未经验证；边界定错的代价高于不做。
- **完全不分层，随用随加**：被否——地基不完备会导致后期改所有调用点（ADR-0025 那九项 hook 就是为此）。

## Consequences

- **内核的设计标准是「完备且最简」**，不是「功能齐全」。判断标准：该概念有没有 hook 让上层挂东西。
- **六条契约现在是类型与接口，不是运行时插件系统**。它们是 M1 设计内核时的硬约束。
- **机制模块（战斗等）先作为内核的一部分实现**，因为只有一套内容。待第二套内容包出现时再抽取。
- **复杂度上限的瓶颈不是"功能多"，是"系统之间怎么交互"**。xkx100（700+ 武功、2000 房间、31 门派）没有插件系统但有强契约（`combat_exp` / `condition` / `valid_learn` / 统一消息模板）——这是本判断的实证支持。
