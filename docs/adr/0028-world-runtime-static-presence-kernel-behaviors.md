# 世界运行时形态：静态在场/动态占用二分 + 内核行为出厂

M1 之后，房间与人物以内容形态落地、出口即命令全链路跑通，但引擎仍零运行时：`CommandDeps.world` 是泛型占位，`SAVE_VERSION = 1` 的迁移链为空，「北」只走到门禁拒绝为止。M2（最小可玩世界运行时：走/看/说）开工前必须定三件事：运行时「实体」指什么、走/看/说的行为归谁、门禁在移动编排的哪一环。本文是这三个定案。

## Context

spec/03 §7 从 Evennia `objects.py`（141KB）提炼了九项「第一天必须定对」的 hook，但 hook 挂在「实体」上——实体是什么没有定案。两个候选模型：

- **Evennia 式全物化**：加载期把每个放置清单条目展开成运行时实体对象（孙彪是一颗对象，两只同类怪是两颗）。
- **静态在场**：NPC 不物化，外观组装时直读房间 `objects[]` 放置清单；只有真正持有可变状态的实体（玩家）进状态树。

同时 M1 留下一个停摆点：命令条目是纯数据，func（执行体）由宿主逐键注入（「效果管线落地前 hosts bind behaviour per command key」）。移动是内核（ADR-0027：内核含「位置与移动」），最小 MUD = 走/看/说（spec/00）——这三个行为归引擎还是宿主，直接决定「换内容不改代码」这条验收标准何时第一次真实可测。

第三件事 spec/03 §7.2 已有原则（`move_to` 不做权限检查），但编排落点（谁查 traverse 门禁、谁查 enter 门禁、查完才调 `moveTo`）需要固定。

## Decision

### 1. 实体 = 动态占用；在场 = 静态直读（二分）

- **动态占用**（runtime entity）：持有可变状态的实体——M2 只有玩家（位置在状态树里，可移动、可接收事件）。走 `Entity` 接口 + hook 运行时。
- **静态在场**（static presence）：NPC 不物化。外观组装（look）直读房间 `objects[]` 放置清单；`count > 1` 的确定性实例 id（`mon-xxx#2`?）难题随战斗/物品才真实。
- **理由**：孙彪在 M2 没有任何可变状态，物化 = 把内容复制进状态树（违背「未显式写入的字段不落盘」，ADR-0022）；`Entity` 接口为将来物化留位——「内核完备性体现在 hook 上，不体现在功能上」（ADR-0027 §2），物化是功能不是架构。
- 九项 hook 按**任意实体**设计；多接收者渲染用测试里的第二假玩家验证；`at_object_creation`/`at_object_post_creation` 两层接缝随 M2 落地（合成实体驱动测试），首个真实消费者是将来的物化票（物品、需要状态的 NPC）。

### 2. 走/看/说/穿行是内核行为，引擎出厂

- 引擎提供 look／say／穿行（traversal）四个通用行为适配器（world runtime + `ContentRegistry` 驱动），宿主绑定即用。
- M1 的「func 宿主注入」是效果管线落地前的停摆点，不是终态；注入缝**保留**——特殊行为仍可覆盖出厂适配器。
- 收益：最小 MUD（走/看/说）零宿主游戏代码，「换一套非武侠内容包，引擎不改一行代码」（验收标准 2）第一次真实可测。
- 目标解析（`TargetRef` → 实体，`cmd-examine` 一类）**不随 M2**——它服务战斗侧目标选择，随那个需求再做。

### 3. 门禁外置于 `moveTo`，编排落点固定

- 穿行适配器的编排顺序：出口 **traverse 门禁**（既有 access 管线）→ 目标房 **enter 门禁**（同一管线）→ `moveTo(entity, target, moveType: "traverse")`。
- `moveTo` 是纯 hook 编排（`at_pre_move` → `announce_move_from` → 容器侧 leave/receive → 位移 → `announce_move_to` → `at_post_move`），**零权限检查**——spec/03 §7.2 的落点确认。
- 拒绝产出 `rejected` + 语义事件（`commandKey`/`errKey` 定位内容 `err_*` 文案），事件按接收者逐一遍历。

## Considered Options

- **Evennia 式全物化**：被否——M2 立刻背上实例 id 与状态复制两个问题；孙彪无状态可持有，物化纯属把内容复制进存档。将来 NPC/物品需要状态时再物化，接口已留位。
- **行为全宿主注入（维持 M1 停摆点）**：被否——走/看/说是内核完备性的具象（最小 MUD 定义），留在宿主侧意味着「换内容不改代码」永远测不了，且每个宿主重复实现一遍。
- **行为等效果管线统一解决**：被否——效果管线是后续里程碑的事，为此冻结现在的内核行为是过度推迟（与硬标准 2 相悖：基础设施第一天做对，但也不为未来冻结当下）。
- **门禁进 `moveTo`**：被否——spec/03 §7.2 已定案（否则每个 hook 都得补一遍检查）；本文重申并固定编排落点。

## Consequences

- **外观组装读两处**：静态在场（放置清单）+ 动态占用（状态树位置索引）——`return_appearance` 是这两处的汇合点。
- **事件接收者集合 = 房内动态占用**（静态在场不消费事件——无 AI 前提下 NPC 不「听」）；渲染层仍按接收者逐一遍历（non-goals B5）。
- **状态树 v1（快照）** = 玩家位置等 M2 结束时的形状；NPC 不进存档（内容即真相，未显式写入不落盘）。
- **测试拓扑**：多接收者/旁观者场景用注入的第二玩家实体驱动，不需要 NPC AI。
- **物化票将来要做的事**：实例 id 方案（确定性）、`at_object_creation` 两层的真实消费者、占用索引从「玩家位置」扩展为「全体实体位置」。
