# 时间换算与日历全内容化，双时钟收敛为同一个推进函数

M4 要给时间和调度落地。本文定这几件事：日历与时间换算**全内容化**（引擎不认识「时辰」）、calendar 的形状是**一组独立的环**、走哪条通道（三分法）、**在线心跳与离线结算是同一个推进函数的两种跨度**（覆盖 ADR-0016 §4「不共用代码路径」）、M4 落哪几个原语、大跨度怎么保证不退化。

## Context

- 硬标准 1「引擎零题材词汇、零硬编码数量」。`spec/04` §3 原稿把 `shichen`／`ke`／`SEASONS` 与 `TICKS_PER_HOUR` 一类换算数字**写进了引擎规格** —— 它们站在硬标准 1 的错误一侧。
- 「时辰」严格说不是武侠题材词（它只是中文历法），但它是**内容**：验收标准 2 要求换包之后连历法一起换。近轨灯塔站（迷你包）被追着问「现在是子时三刻」就是验收标准 2 破功。
- ADR-0016 §4 定了**双时钟**（在线心跳 tick / 离线结算）并要求「**不共用代码路径**」。当时的顾虑是两者语义不同：离线只补资源，不能自动战斗。但「两条代码路径」不是表达这个顾虑的唯一方式 —— 差异其实是**跨度**，不是**机制**。
- ADR-0022 §5 / ADR-0025 §四要求「时间推进**按需求值**」，否掉每 tick 遍历。
- ADR-0025 §三把调度定为六个原语并明说「可砍到四」。

## Decision

### 1. 日历全内容化；引擎只有 `f(环, tick) → 段索引`

段名、段数、每段多长、有哪些刻度轴，全部住在 `content/config/calendar.json`。引擎**不知道**什么是时辰，也不知道什么是季节。

**没有默认公历兜底**：包没给 `calendar`，用到时间时**大声失败**。给兜底等于让「忘记配日历」变成一种静默的、带着别人历法的错误。

### 2. 形状是一组独立的**环**（ring），不是一张扁平分段表

```
{ "id": "calendar",
  "rings": [
    { "id": "day",  "segments": [ { "id": "zi",   "ticks": 2400 }, … ] },
    { "id": "year", "segments": [ { "id": "chun", "ticks": …    }, … ] }
  ] }
```

一个 tick 同时落在**多条**刻度轴上（日内是「哪个时辰」，年内是「哪个季节」）。一张扁平分段表只能表达一个环 —— **后来想加季节就得改 schema + 改引擎**，这正是「面向未来：MVP 只控制系统数量，**不降低架构完备度**」要防的那种返工。

**环周期 = `Σ segments[].ticks`**，不另设字段 ⇒ 没有第二个数需要同步（不让 `settings.time.ticksPerDay` 与环周期各说一遍，与 ADR-0031 §4「不保留两个真相」同律）。环之间互相独立，各自取模；引擎不关心 `day` 与 `year` 是否成 360 倍关系 —— 那是数据的事。

### 3. 三分法：calendar 归 STRUCTURE，速率归 TUNING

`08-non-goals.md` C4 明写 **STRUCTURE 不进 `settings`**。段名与段数是装配图，所以拆两处：

| 文件 | 归类 |
|---|---|
| `content/config/calendar.json`（新，配套 `schemas/config.calendar.schema.json`） | **STRUCTURE** |
| `content/config/settings.json` 的 `time` 组（回复速率、buff 时长、冷却默认，键名带 tick 单位） | **TUNING** |

⚠️ **不属于这两处的**：ADR-0016 §4 提到的 `tickSeconds`（一个 tick 等于多少**真实秒**）。它是宿主把墙钟翻译成 tick 的参数，**引擎不读**（引擎只认 tick），因此不进 `content/config/settings.json` —— 那是给引擎的 TUNING。它的落点由宿主票定（见 `spec/04` §6 O5）。

走与 `dimensions` **同构**的通道：`createContentRegistry(content, { dimensions?, settings?, calendar? })`，宿主装载器读 `config/` 后传入（引擎不读文件）。注册表校验跨字段一致性（环周期 > 0、段 id 环内唯一）—— schema 管不了的那类约束，与今天的引用完整性同一层。**缺失时由引擎侧在首次使用时间时大声失败**，不是注册表加载期：注册表不该知道引擎需要哪些参数。

### 4. 双时钟降级为同一个推进函数的两个跨度

**在线心跳 = 跨度 1；离线结算 = 跨度很大；到期桶 = 跨度内的到期项。** 三者是同一个 `settleTo`。

**推进的触发点还有一个必须定的边界**：只有**进入执行段**的命令（`ok`／`rejected`）才推进世界；`invalid`（无法解析）不推进，其 `tick` 也不抬高 `maxTick` —— 否则玩家发一堆乱码就能快进世界。时间与 `seq` 同律（`invalid` 不消耗 seq，见 ADR-0025 §1.2）。详见 `spec/04` §4.1。

> ⚠️ **本文覆盖 ADR-0016 §4 的「不共用代码路径」**。被保留的那一半更重要，重述一遍：**离线补算只补资源与基础熟练度**（有上限），**不自动战斗、不推层、不产掉落**。这条约束改由**内容配了哪些离线补算项**来表达，而不是靠「另写一套离线代码」。

### 5. M4 落四个原语，另两个留给消费者

保留：Clock（高水位）／纯 stage 求值／观察时补偿结算／到期桶。
不落：**区域 tick** —— 它是六个里唯一复杂度为 **O(跨度 / interval)** 的原语，且今天没有订阅者（天气、区域驻守刷新的事）；**on-change** —— 属于状态层不是调度层。

接缝写进 `spec/04` §4.1，避免将来被当成「忘了做」而悄悄侵蚀：区域 tick 的插入点是「一条跨度内的分组订阅」，on-change 的插入点是「状态树写入钩子」，两者都不需要改 `settleTo` 自身。

### 6. 大跨度不加数值上限，靠构造性保证

不加 `settings.time.maxCatchUpTicks`：截断会让世界状态依赖**玩家多久上线一次**，违反「世界不因观察而不同」；而且那是个会改变游戏语义的写死护栏数字（跟 `caps.maxConcurrent*` 那种不改变语义的技术护栏不是一类）。

替代：**所有原语必须是 O(事件数) 而非 O(tick 数)**（这在第 5 条砍掉区域 tick 之后成立），并**用一条测试钉死**（推进 100 万 tick，断言迭代次数／耗时上界）。写法照本仓既有口味：「出口不可继承是构造性的」、「不可混淆是构造性保证」。

## Considered Options

| 方案 | 否掉的理由 |
|---|---|
| **常量进 config、日历词留引擎**（「中文历法属于中文层」） | 迷你包被迫说「子时三刻」，验收标准 2 破功；且「时辰」仍在引擎里 |
| **日历整体塞进 `settings.time`** | 违反 C4 三分法；且 `settings` 顶层九类封闭、组内开放，塞结构进去就得改顶层封闭这个约定 |
| **新开内容集合 `content/time/`** | 概念最正，但要动集合清单与 `common.schema.json` 的 14 处 `$ref`，收益不成比例 |
| **给跨度加 `maxCatchUpTicks` 上限** | 世界状态依赖玩家上线频率；且截断丢失的事件无法追回 |

## Consequences

- 新增一个 schema（`config.calendar.schema.json`）⇒ 走 **ADR-0003 三处同步**：`core` 类型 / 编辑器表单 / `docs/agents/content.md` 的 config 清单。
- `docs/spec/04` §3 的 `shichen`／`ke`／`SEASONS` 写法被替换（spec 是活规格，就地更正；ADR-0016 本身不回改）。
- 武侠包与迷你包各需要一份自己的 `calendar.json`，且**维度表式的「换目录即换包」延伸到历法**。
